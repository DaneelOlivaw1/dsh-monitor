# 铺治理骨架

**不是复制模板，是给这个项目配一套合身的。** 复制会造出两套并存的东西，比没有更糟。

模板只当参考：`<plugin>/templates/governance/`（角色 / 流程 / 闸门 / 台账的骨架）。

## 一、先读，别先写

按顺序看，缺哪样记下来，**不要边说边改**：

1. `AGENTS.md` / `CLAUDE.md` —— 已有入口？是否已经分层？（很多项目已经有，只是没闸门）
2. `agents/` 或 `.pi/agents/` 或 `.claude/agents/` —— 已有角色？边界写了吗？
3. `memory/` 或 `.memory/` —— 已有台账？索引在不在？条目格式统一吗？
4. `docs/` —— 有没有 dispatch 协议、开发流程、ADR？
5. `.dsh/gates.yml` —— 有闸门吗？
6. 语言与命令：`Cargo.toml` / `package.json` / `pyproject.toml`；测试、构建、格式化的真实命令。

## 二、只补缺的那层

| 已有情况 | 动作 |
| --- | --- |
| 有 AGENTS.md 且已分层 | 不动，只在它的「记忆索引」加一行指向新文档 |
| 有 AGENTS.md 但一坨 | **重写成四层结构**：先把它现有的规则逐条摘出来，重排进「四层结构 + 冷启动顺序」；细节搬进 `docs/`，入口只留指针。重写后逐条核对，原有条目一条不少（搬进 `docs/` 也算保留） |
| 有 agents/ | 只补缺的角色；已有的按「不做什么」检查一遍，缺就补一段，不改职责 |
| 有 memory/ | 沿用它的索引与条目格式；缺 `TEMPLATE.md` / 缺索引行就补，**格式不对就地改对**（见下「台账格式」） |
| 没有 `.dsh/gates.yml` | 新建，只放这个项目真用得上的闸门（3–5 条，宁少不多） |

**不设新增文件数上限。** 分层治理本来就要多文件，卡数字只会把内容硬塞进少数几个文件里。判据换成「有没有归位」：每个新文件必须挂在四层之一，且被 `AGENTS.md` 或 `memory/MEMORY.md` 指向——没有入口的才是硬塞。

### 台账格式（防腐化的重点）

`memory/` 只认这两样格式，别的写法都算漂移：

- `MEMORY.md` 索引：`- [[name]]：一句话说明 +（何时必读）`，一行一条，按名称插进对应分区。
- 条目文件：frontmatter 只认 `name` / `description` / `type`；`type` 取值只能是 `必保行为 | gotcha | runbook | reference | project`；正文按 `TEMPLATE.md` 的「涉及文件 / 必保行为 / 回归测试」写。
- 新增条目必须在同一轮加索引行；只写条目不加索引 = 台账失联。

已有条目不按这个格式：**改格式，不改事实**——补字段、纠 type、拆开一条里堆的多个教训、补缺失的索引行。改完在汇报里列出改了哪几条，别静默改。理由：索引一旦失准，就没人再翻台账，这一层等于没铺。

## 三、按项目定制（关键）

不许原样搬模板里的命令与角色：

- **命令**：闸门和流程里写的测试/构建/格式命令，必须换成这个项目真实跑的（从 `package.json` / `Cargo.toml` / Makefile 里读出来）。
- **角色**：只保留这个项目真的会派的角色。纯前端项目可能没有 `deploy-ops`；数据项目可能没有 `developer`。
- **交付证据**：这个项目「什么算完成」写具体——网页是截图，API 是库行，CLI 是退出码。证据放 `plans/NNNN-YYYY-MM-DD-标题/evidence/`，跟着计划、跟着 git 走（见下节）。
- **红线**：从这个项目已有的规则里抄（不许 unsafe / 金额用定点数 / 生产库只读），别用模板的默认红线。

## 四、交付证据跟着计划走

证据不散在聊天记录和临时目录里，也不另起顶层目录——它是计划的一部分：

```
plans/NNNN-YYYY-MM-DD-标题/
├── task_plan.md          计划 + 验收标准
└── evidence/             交付证据，进 git
    ├── INDEX.md          验收项 → 证据文件，一行一条
    ├── 01-home.png       网页：最终态截图（关键路径各一张）
    ├── api-create.txt    API：真实请求 / 响应，或库行查询输出
    └── cli-test.log      CLI：命令 + 输出 + 退出码
```

- **编号只有一处**：`plans/NNNN-YYYY-MM-DD-标题/` 是唯一编号源，`evidence/` 直接放在它下面，不另建目录映射。
- **`INDEX.md` 只三列**：`| 验收项 | 证据文件 | 怎么看 |`，一行一条，不写议论文。

```markdown
| 验收项 | 证据文件 | 怎么看 |
| --- | --- | --- |
| 首页正常加载 | `01-home.png` | 打开截图看首屏 |
| 创建订单成功 | `api-create.txt` | 响应原文里有 order_id |
| CLI 全绿 | `cli-test.log` | 末行 `exit 0`，28 passed |
```
- **证据形态按交付物定**：网页 / 界面 = 截图（看得到最终态，别只截控制台）；API = 库行或响应原文；CLI / 脚本 = 命令 + 输出 + 退出码。
- **可复核**：`INDEX.md` 每行写清「验收项 → 文件」，必要时补一句怎么重跑（命令、路径、时间点）。
- **只追加不覆盖**：结论被推翻就加新文件，INDEX 里把旧行标作废，不删旧证据。
- 声称「完成 / 修好 / 上线」时，闸门 `deliver-with-evidence` 验的就是 `INDEX.md` 每行指针能落到真实文件。

## 五、闸门只要必要条件的

每条闸门写三样：`when`（什么时候判）、`require`（判什么）、`enforce`（block / warn）。

判据必须能机械判：能不能数、能不能 grep、能不能跑脚本。
**判断不了的一律不要做成闸门**（比如「代码写得好不好」），写成流程里的一句话就行。

默认只放这几条（按项目取舍）：

1. 改代码前有计划文件
2. 测试先红（有一次失败记录早于源码改动）
3. 评审 PASS 才合并
4. 说完成要带证据（L1 界面 + L3 库行，且 `plans/NNNN-*/evidence/INDEX.md` 指针可解析）
5. 子代理报告非空（防早退）

## 六、汇报格式（固定）

```
读完的现状：<已有 agents / memory / docs / 命令>
新增：<文件: 一句话为什么>
改动：<文件: 改了什么、依据（重排 / 改格式 / 补缺）>
证据：<plans/NNNN-*/evidence/ 里新增了什么>
闸门：<id: 判据 + block/warn>
没动：<哪些已存在所以跳过>
下一步：<这个项目应该先补哪一层>
```

## 边界

- **不覆盖**已有文件；两处例外：`AGENTS.md` 一坨时按四层重排（规则逐条保留）、`memory/` 格式漂移时就地改对（只改格式不改事实）。要改先说改哪几行。
- **不搬家**：已有的 `memory/`、`agents/` 原地不动，不许合并成新目录。
- **证据不另建顶层目录**：跟着 `plans/NNNN-*/` 走，别出现根目录级的 `evidence/`。
- **不写代码**：只铺骨架，不实现功能。
- 铺完不 commit（等用户看过）。
